# Coxi Recipe Calculator: Context for LLMs

This file gives an AI assistant what it needs to change this project safely. It describes the project, the rules, the decisions and the history, and it includes open points and known problems. Read it before you change anything.

> **Developed with AI.** This project was written by Claude (Anthropic), an AI assistant, following prompts from the maintainer, who defined the requirements, tested the app and made the design decisions. Commits that contain AI-written code carry a `Co-authored-by: Claude` trailer.

## 1. What the project is

A static web app (GitHub Pages, no server) that plans cooking for groups. It takes a list of planned recipes with portions and dates, the number of people and an optional stock inventory, and produces:

- summed ingredient amounts, minus the inventory,
- packages to buy and two price figures (value of the food used, purchase total in whole packages),
- four A4 PDFs: recipes, sorting list by recipe type, container labels, shopping list grouped by shop.

It also contains editors for recipes and ingredients, which store changes in the browser. Repository data changes only through pull requests.

The maintainer is not a professional developer. The maintainer wants clean, readable code. Clarity beats extra features. Avoid clever abstractions and unnecessary helper functions, but also avoid one file per function. The maintainer prefers complete file replacements over line-by-line changes when code is delivered.

## 2. Hard constraints

- **No build step, no bundler, no TypeScript.** Plain ES modules run directly in the browser. Type checking uses JSDoc and `// @ts-check`.
- **No runtime dependencies except the vendored pdfMake and qrcode-generator.** Do not add npm packages to the site. Development dependencies are allowed for tests and checks (currently only `ajv`).
- **Everything in English:** code, comments, UI texts, error messages, data, documentation. The development conversation is in German, the repository is not.
- **Works offline** after the first visit. New files must be listed in `SHELL_FILES` in `sw.js`.
- **No network calls** except loading the app's own static files. No analytics, no external APIs.
- **Privacy:** plan, inventory and local changes stay in the browser (local storage). Only public recipe and ingredient data is in the repository.
- **Mobile and desktop**, including iOS Safari and DuckDuckGo on iOS.
- **GitHub Action must stay YAML.** GitHub only runs workflows from YAML files.
- Keep the **calculation unrounded**. Rounding happens only in display (`format.js`) and in package counts.

## 3. Data model (the rules that matter)

- Units are **free text** (`g`, `kg`, `l`, `ml`, `piece`, `can`, `clove`, `bulb`, ...). There is no enum and no built-in conversion. Each ingredient has exactly one unit, used everywhere: recipes, inventory, shopping list, price.
- Conversions only happen through explicit factors when the user changes a unit (see section 6).
- Recipe `servings` (default 1) is the number of people the amounts are written for. Needed amount = `amount × portions / servings`.
- `portionWeight` (g) is optional and display only, unless the user scales with the scale button.
- Ingredient `packageSize` and `packagePrice` must be given together. Missing price data is normal: "-" in the shopping list, the totals become lower bounds.
- Inventory export: `{ schemaVersion: 1, kind: "inventory", name, items: { id: amount } }`. Name is required, amounts are in the ingredient unit, no unit field.
- Recipe ids and file names match. `recipes/index.json` is generated by `npm run build-index` and updated by the GitHub Action on same-repo pull requests.
- No allergen field. Labels list all ingredients. Allergens are highlighted by hand.
- A recipe can be planned several times, also on the same day.

## 4. Architecture in short

- `js/core/`: pure rules and calculation, no DOM. This is where logic belongs, and it is tested.
- `js/pages/`: one entry module per page. Each page wires components together.
- `js/ui/`: DOM components used by the pages.
- `js/data.js`: `loadAppData(prefix)` loads repository data and merges local changes. All pages use it.
- `js/storage.js`: the only module that touches `localStorage`. Keys: `coxi-plan`, `coxi-inventory`, `coxi-recipes`, `coxi-ingredients`.
- `js/pdf/documents.js`: all PDF definitions.
- `sw.js`: network first, cache as fallback, navigation requests cached without query string.
- `scripts/`: data check and index generation, run by `npm run validate` and `npm run build-index`.
- `css/style.css` (general look, reusable) and `css/app.css` (layout and screen adjustments). Someone who wants the same look only needs `style.css`.

## 5. Current behavior and decisions

### 5.1 Main page

- Sections Mains, Spreads, Others. Each row: date (weekday button, date input on touch screens), recipe (search with suggestion list, filtered by section type), portions, remove button.
- New rows get the global number of people as portions. Choosing a recipe does not change them.
- Empty rows are ignored. An unrecognised recipe name is marked red and ignored.
- Default people: 100 (`DEFAULT_PEOPLE` in `planner.js`).
- Results are hidden when the plan or the people change (compared with a snapshot), and when an inventory is loaded or removed. The event name does not hide them, because PDFs read it at click time.
- The plan is written to the address and to `coxi-plan`. An address without query string restores the saved plan.
- Sharing: copy link, native share (only where supported), paste link. Pasting replaces the plan only after confirmation. The inventory is not part of links and is never replaced by pasting.
- Settings dialog (gear icon) title is still "Share plan". The maintainer decided to keep it.

### 5.2 Inventory

- Stored in `coxi-inventory` and saved on every change. Export and import as JSON (name in file name), PDF export.
- Main page can load an inventory file and remove it. Inventory editing happens only on the inventory page.
- Inventory files from other people carry no unit information. Their amounts are taken as they are.

### 5.3 Recipes page

- List by type with search. JSON and PDF button per recipe. New recipe. Import of a recipe file (saved locally, no merge needed).
- Editor: name at the top, type, servings, portion weight, ingredients with search, working steps. Scale button in the "Ingredients" heading appears when servings or portion weight change and disappears after scaling. Nothing is saved until "Save in this browser".
- Save stores locally and the main page uses it after reload. "Download recipe file" creates the repository format file for a pull request.
- Discard button: "Discard local changes" for repository recipes, "Delete recipe" for local ones. Both ask first.

### 5.4 Ingredients page

- List by category with search, showing names only. Marker "Changed in this browser" or "Saved in this browser only".
- Editor: name, unit, category, package size, package price, shop. Unit change shows a panel with two amount fields (both 1 by default), factor = new / old.
- Saving with a unit change converts: local recipe copies using the ingredient, the stored inventory amount, the package size. Package price stays. Repository files are not changed.
- Delete only for local ingredients that no recipe uses. Discard for repository ingredients.
- Export: complete `ingredients.json` with all local changes. Import: identical entries are not stored locally; entries with a different unit open the conversion dialog; cancel imports nothing.
- No success messages are shown on save or import (the maintainer asked to remove them).

### 5.5 Pull request workflow

- Users download a recipe or ingredient file, add it to `recipes/` or `ingredients/ingredients.json`, and open a pull request. The maintainer merges. The Action updates `recipes/index.json` on same-repo pull requests.
- Forks cannot be updated by the Action. Their index must be correct before the pull request is opened.
- Recipe and ingredient imports in the app are local only. They are not merged into the repository.

### 5.6 Help links

The "? Help" buttons on the recipe and ingredient pages point to `#` until the public repository URL exists. The target is the user guide, section "Changing and uploading recipes": `docs/USER_GUIDE.md#changing-and-uploading-recipes`. Renaming that heading changes the anchor.

## 6. Unit change: how it works and what it does not do

- A unit change is applied by `convertUsage` in `js/pages/ingredients.js`: recipes that use the ingredient are re-read from the merged data, their amounts multiplied, saved as local copies (`convertRecipeAmounts`), the stored inventory amount is multiplied (`convertStoredInventoryAmount`), and the package size is multiplied.
- It is applied at save time and at import time (after the dialog).
- Several conversions in a row stack up, because the data is re-read each time.
- The factor is always `new amount / old amount`. Both fields must be greater than 0.

### 6.1 Known bug (not fixed, accepted for now)

**Symptom:** A unit is changed with a conversion, for example `clove → g` with factor 3. The recipe amounts change correctly (2 clove → 6 g). Then "Discard local changes" is pressed for that ingredient. The unit goes back to `clove` without any conversion, so the recipes now say 6 clove where 2 clove were meant. The amounts are wrong.

**Cause:** The discard only removes the local ingredient record. The local recipe copies and the stored inventory keep the converted values, and nothing records which unit the amounts of each recipe are written in.

**Affected flows:** discard of a repository ingredient with a local unit change; the same happens with "Delete ingredient" if the ingredient is in use, which is blocked, so it is mainly the discard case.

**Proposed solution, not implemented, discussed with the maintainer:**

1. Store the conversions in the ingredient record: an ordered `unitHistory` of steps `{ from, to, factor }`. Each new conversion appends a step. The current unit is the `to` of the last step.
2. Discard then applies the steps in reverse, each with `1 / factor`, to the recipes and the inventory, and restores the repository unit.
3. Keep a record of the unit each recipe amount is written in, for example a separate local key `coxi-recipe-units`, `{ recipeId: { ingredientId: unit } }`, with the repository unit as default when an entry is missing. Only recipes whose record is still at the old unit are converted, and discard converts a recipe from its recorded unit back to the repository unit. This is needed because a recipe saved after the change is already in the new unit and must not be converted back.
4. Import: if the importing ingredient has a history step whose `from` equals the local unit, the remaining steps can be applied without a dialog. The dialog remains for ingredients without a matching history.
5. Existing local changes without history cannot be reconstructed reliably. A one-time notice would be needed.

**Maintainer decision so far:** the fix is postponed. The bug is documented as known in the user guide (short warning, no programming advice) and in the technical documentation.

Also note: an ingredient's history is only meaningful if it is kept in the repository file when a user sends the ingredient list to someone else. That is why the proposal puts the history inside the ingredient record.

## 7. Decisions made and why

- **Static site, no backend, GitHub Pages:** keeps hosting free and avoids storing personal planning data on a server.
- **Recipes and ingredients in JSON, one recipe per file:** small, reviewable pull requests and readable diffs. The ingredient list stays in one file so ids are unique.
- **Free-text units, no conversion table:** the maintainer wanted to avoid conversion logic. Units such as `clove` or `bulb` must be possible without changing code.
- **Missing data is allowed:** recipes and calculations must work without portion weight, prices, shops or categories.
- **Inventory in localStorage** (not only as a file): the maintainer wanted it to stay between visits. The file remains the way to share it.
- **Inventory name is required in the file:** so a file has a visible identity on the main page.
- **Plan in the address:** makes plans shareable as links and QR codes, and works with a home screen app through the saved plan.
- **Recipe index generated automatically:** users should not need to edit `recipes/index.json`.
- **Scale button instead of a checkbox:** the scale is applied live on press, not on each change, and does not move the page.
- **Results hide on change instead of recalculating silently:** the maintainer wanted to decide when to recalculate.
- **Datalist replaced by a custom suggestion list:** shows all options when empty and works on mobile.
- **Date picker overlay only on touch devices:** on iOS, the picker opens only from a tap on the input itself; on desktop, `showPicker()` is used.
- **Network-first service worker:** changes arrive without manual cache version changes. The cache version is only bumped when files move.
- **Shopping list only as PDF** on the main page. The price estimate stays on screen.
- **Print labels per planned row**, so two pots of the same recipe get two labels.
- **Thousands separator is a space**, decimals a dot.
- **English everywhere** in the app, but the maintainer works in German. Keep answers in German when talking to the maintainer, and English in the repository.

## 8. Rejected or dropped ideas

- TypeScript and any build step (rejected: too much infrastructure for the maintainer).
- A unit enum in the schema (rejected: units must be free).
- Unit conversion tables per ingredient (rejected, see 5.4 and 6).
- An allergen field (rejected: the same recipe may be prepared with different allergens, the maintainer marks them by hand).
- Compressed query strings for inventories (rejected: inventory goes into a file).
- A JSON format for the GitHub Action (not possible, GitHub reads only YAML).
- Lighthouse "Installable" check (removed from recent Chrome versions, the DevTools Application panel is used instead).
- Spin buttons on number fields (removed, typing is enough).
- A dropdown for recipes (replaced by a searchable suggestion list).

## 9. Differences from the original specification

The first specification (`docs/PROJECT_SPECIFICATION.md`) has been deleted by the maintainer, so this list records the deviations for future reference:

- Data is in top-level folders (`ingredients/`, `recipes/`, `inventory/`), not in `data/`.
- The inventory is also kept in `localStorage`, and inventories carry a `name`.
- Ingredient edits and recipe edits are kept in the browser immediately, not only as files.
- The recipe index is generated and committed by the GitHub Action.
- The service worker uses network first. The reminder to bump the cache version in the validation action was not implemented.
- The workflow file is `validate.yaml`.
- Shopping list is not displayed on the main page, only as PDF.
- Unit conversion on changes is a feature (it was not in the original spec).
- Inventory unit conversion happens only for the stored inventory on the same device.

## 10. Open points

These are not decided or not implemented. Ask the maintainer before you build any of them:

1. **Discarding a unit conversion (section 6.1).** The proposed solution is above.
2. **Recipe names are not unique per type.** The plan finds recipes by name within a section. Two recipes with the same name in one section make the choice ambiguous. The maintainer has not decided whether to validate this in the data check or in the editor.
3. **Inventory files from others have no units.** An inventory exported in a different unit is taken as it is. Possible fixes: add a unit to inventory entries, or check against ingredient units on import.
4. **Service worker updates are silent.** There is no message that a new version is available.
5. **Cache version reminder** in the validation action was planned and not implemented.
6. **Home screen apps on iOS** have a separate storage, so the plan and inventory do not appear there unless they are shared again.
7. **Allergens** are marked by hand on the labels. A future allergen field was discussed and dropped for now.
8. **Recipes with the same ingredient in different units** from two separate imports are not reconciled. The unit history proposal would handle this.
9. **Calculation of a changed portion weight in the core** (`changePortionWeight`) is tested but not used by the UI. It can be removed or used.
10. **Shopping list on screen** was removed by the maintainer. It may come back as an option, but no decision was made.

## 11. Checklist for changes

1. Read the relevant module in `js/core/` first. Put rules there, not in the page.
2. Keep the calculation unrounded. Round only for display.
3. Use English for everything you write, including comments and messages.
4. New file: add it to `SHELL_FILES` in `sw.js`. Moving files: bump `CACHE_VERSION`.
5. New or changed data rule: update the JSON Schema and the matching rules in `js/core/`, then add tests.
6. Changed data files: run `npm run build-index` if recipes changed, then `npm test` and `npm run validate`.
7. Changed styles: general look in `style.css`, screen-specific rules in `app.css`.
8. No new runtime dependencies, no build step, no external network requests.
9. Do not store personal calculation data in the repository.
10. Update the documentation files only as the maintainer asks. The three user and developer documents describe the current state. This file may also describe open points and history.
