# Coxi Recipe Calculator: Technical documentation

> **Developed with AI.** This project was written by Claude (Anthropic), an AI assistant, following prompts from the maintainer, who defined the requirements, tested the app and made the design decisions. Commits that contain AI-written code carry a `Co-authored-by: Claude` trailer.

## 1. Overview

The Coxi Recipe Calculator is a static web app. It is served as plain files, for example by GitHub Pages, and has no build step, no server and no database.

- **Language:** plain JavaScript with ES modules, no TypeScript, no bundler. Files are checked with JSDoc comments and `// @ts-check`.
- **Runtime dependencies:** pdfMake 0.2 with the Roboto font (`vendor/pdfmake/`) and qrcode-generator (`vendor/qrcode-generator/qrcode.js`). Both are shipped in the repository and loaded as classic scripts, so the app works offline.
- **Development dependencies:** `ajv` (JSON Schema validation) for tests and the data check. Tests run with the Node test runner.
- **Data:** public recipes and ingredients are JSON files in the repository. Calculation data (plan, inventory, local changes) is stored only in the browser's local storage.
- **Target:** desktop and mobile browsers, installable as a progressive web app.

## 3. Data formats

All data files carry `"schemaVersion": 1`. IDs are lowercase kebab-case and match `^[a-z0-9]+(-[a-z0-9]+)*$`. IDs are never changed after release. Units are free text, and the app never converts between units except through explicit conversion factors.

### 3.1 Ingredient

```json
{ "id": "garlic", "name": "Garlic", "unit": "clove", "category": "Vegetables",
  "packageSize": 10, "packagePrice": 0.45, "whereToBuy": "Weekly market" }
```

- `id`, `name`, `unit`: required.
- `category`, `whereToBuy`: optional free text.
- `packageSize` and `packagePrice`: optional, but must be given together (`dependentRequired` in the schema). Package size is in `unit`.

### 3.2 Recipe

```json
{ "schemaVersion": 1, "id": "chili-sin-carne", "name": "Chili Sin Carne", "type": "main",
  "servings": 4, "portionWeight": 400,
  "ingredients": [ { "ingredientId": "onion", "amount": 2 } ],
  "steps": ["Dice the onion."] }
```

- `type`: `main`, `spread` or `other`.
- `servings`: integer ≥ 1, default 1. The ingredient amounts are written for this many people.
- `portionWeight`: optional, display only, in grams.
- `ingredients`: at least one entry. `amount` > 0.
- `steps`: at least one non-empty text.

### 3.3 Inventory export

```json
{ "schemaVersion": 1, "kind": "inventory", "name": "Inventory August 2026",
  "items": { "olive-oil": 500, "onion": 3 } }
```

- `name` is required. Amounts are numbers ≥ 0 in the unit of the ingredient. There is no unit field.
- Unknown ids are skipped with a warning when the file is loaded.

### 3.4 Recipe index

`recipes/index.json` lists every recipe id once, sorted. It is generated by `scripts/build-index.js`. The app loads it to know which recipe files to fetch, because a static site cannot list folders.

### 3.5 Plan in the address

The plan is stored in the query string of the page:

```
?p=6&e=Nebu%202027&r=chili-sin-carne:6@2027-02-27,pancakes:2
```

- `p`: number of people (whole number ≥ 1). Default when missing: 100.
- `e`: event name, URL-encoded, optional.
- `r`: comma-separated rows `recipe-id:portions` with optional `@YYYY-MM-DD`. A recipe can appear several times.

Invalid entries are skipped with a notice. Unknown recipe ids are reported as missing.

## 4. Local storage

All keys are written by `js/storage.js`. Every access is wrapped in `try`/`catch`, so the app still works if storage is unavailable.

| Key | Content |
|---|---|
| `coxi-plan` | Last plan query string. Restored when the main page is opened without a query string. |
| `coxi-inventory` | Current inventory in the export format (`buildInventoryFile`). |
| `coxi-recipes` | Object of saved recipes by id. A saved recipe replaces the repository recipe with the same id. |
| `coxi-ingredients` | Object of saved ingredients by id. Same replacement rule. |

**Delete all local data** (settings menu) removes all four keys.

Merging rule for recipes and ingredients (`mergeRecipes`, `mergeIngredients`): repository entries are taken as they are, saved entries with the same id replace them, and saved entries without a repository counterpart are appended.

## 5. Modules

### 5.1 Core (`js/core/`, no DOM access)

- **`utils.js`:** `indexById`, `requireIngredient`, locale-aware sorting (`compareText`, `compareNullableText`), `isPlainObject`.
- **`types.js`:** JSDoc typedefs only (`Ingredient`, `Recipe`, `Inventory`, `ShoppingItem`, `ShoppingGroup`, `PriceSummary`).
- **`recipes.js`:**
  - `getServings`, `getScaleFactor(recipe, people)`
  - `calculateNeededAmounts(entries)`: sums `amount × portions / servings` per ingredient, not rounded.
  - `sumAmountsByType(entries, ingredientsById)`: amounts per recipe type, for the sorting list.
  - `groupIngredientNamesByType`: names per type, used in tests.
  - `changePortionWeight`: exists and is tested, but the UI does not call it.
  - `mergeRecipes`
- **`planner.js`:** `resolvePlan(rows, recipesById)` returns the planned entries and missing ids. `encodePlanUrl` and `parsePlanUrl` convert between rows and the query string.
- **`shopping.js`:**
  - `buildShoppingItems(needed, inventory, ingredientsById)`
  - `summarizePrices(items, people)`
  - `groupByShop(items)`
- **`inventory.js`:** `parseInventory`, `buildInventoryFile`, `DEFAULT_INVENTORY_NAME`.
- **`recipe-editing.js`:** `slugify`, `createUniqueId`, `validateRecipeDraft`, `buildRecipeFile`, `readRecipeFile`, `scaleFactorForChange`.
- **`ingredient-editing.js`:** `validateIngredientDraft`, `buildIngredientRecord`, `readIngredientFile`, `buildIngredientsFile`, `mergeIngredients`, `isSameIngredient`, `usingRecipes`, `convertRecipeAmounts`, `groupByCategory`, `roundAmount`.
- **`format.js`:** number, money, percent and date formatting. Thousands are separated by a space, decimals by a dot. Rounding happens only here, never in the calculation.
- **`validation.js`:** `validateDataset`, the relation checks between data files.

### 5.2 Pages (`js/pages/`)

Each page is one module that is loaded with `<script type="module">` from its HTML file.

- **`main.js`:** loads the data with `loadAppData`, connects the planner, the inventory import, the share dialog, the calculation and the PDF downloads. Keeps the calculation snapshot that decides when results are hidden.
- **`inventory.js`:** edits the stored inventory, search, JSON and PDF export, file import.
- **`recipes.js`:** list, search, JSON and PDF per recipe, new recipe, import, editor integration.
- **`ingredients.js`:** list, search, editor integration, export, import with unit conversion dialog, discard and delete rules.

### 5.3 Shared loader (`js/data.js`)

`loadAppData(prefix)` loads `ingredients/ingredients.json`, `recipes/index.json` and all recipe files, relative to the page (`""` on the main page, `"../"` on subpages). It returns the repository data and the merged data.

### 5.4 Components (`js/ui/`)

- **`planner.js`:** the three sections, rows, recipe suggestion list, date picker, portions. Writes the query string through the page.
- **`results.js`:** the four download buttons and the price estimate.
- **`share.js`:** settings dialog. QR code (SVG generated by qrcode-generator, white background removed), copy, native share, paste, replace confirmation.
- **`inventory-import.js`:** inventory section of the main page.
- **`recipe-editor.js`:** recipe form, scale button, ingredient search rows, working steps, validation messages.
- **`ingredient-editor.js`:** ingredient form, unit conversion panel, and the conversion dialog used by the import (`askUnitConversions`).
- **`fit-input.js`:** sets the width of the title and number fields to their content. The title takes the full width while it has the focus.
- **`reset-data.js`:** the "Delete all local data" button.

### 5.5 Other modules

- **`js/pdf/documents.js`:** all pdfMake definitions (recipes, sorting list, labels, shopping list, inventory). Each function returns a plain object. The caller creates the file with `pdfMake.createPdf(definition).download(name)`.
- **`js/storage.js`:** local storage access, see section 4.
- **`js/pwa.js`:** registers `sw.js` with a path relative to the module.

## 6. Main flows

### 6.1 Planning and calculation

1. The planner reads its rows from the page. Rows without a recognised recipe are ignored.
2. `resolvePlan` turns the rows into entries (recipe, portions, date). Missing ids are reported.
3. `calculateNeededAmounts(entries)` sums the amounts.
4. `buildShoppingItems` subtracts the inventory and computes packages and prices.
5. `summarizePrices` builds the totals.
6. The results are rendered. The page stores a snapshot of people and rows. If the plan or the people change later, the results are hidden. Changing the event name does not hide them. Loading or removing an inventory hides them too.

The plan is written to the address bar and to `coxi-plan` on every change.

### 6.2 Inventory

- The main page loads the stored inventory (`coxi-inventory`) at start, and can load or remove a file.
- The inventory page saves every change at once through `saveStoredInventory`. An empty amount removes the entry.

### 6.3 Recipe editing

- The editor works on a draft, validated by `validateRecipeDraft`. The first successful save or download fixes the id, which is made from the name with `createUniqueId` (duplicates get `-2`, `-3`, ...). Later name changes keep the id.
- **Save in this browser** stores the recipe in `coxi-recipes`.
- **Download recipe file** creates `<id>.json` in the repository format.
- The **Scale ingredients** button appears when servings or portion weight differ from the base values of the form. Its factor comes from `scaleFactorForChange`: `servings ratio × weight ratio`, where the weight ratio is used only if both weights are set. The amounts are multiplied in place, nothing is saved, and the new values become the base.

### 6.4 Ingredient editing and unit change

- The ingredient editor validates with `validateIngredientDraft` and stores the record in `coxi-ingredients`.
- If the unit differs from the saved unit, the panel asks for two amounts (both 1 by default). The factor is `new amount / old amount`.
- On save with a factor, the page (`convertUsage`):
  1. multiplies the amounts of the ingredient in every recipe that uses it (saved as local recipe copies, `convertRecipeAmounts`),
  2. multiplies the stored inventory amount (`convertStoredInventoryAmount`),
  3. multiplies the package size. The package price is not changed.
- Repository recipes are not changed. The changes are local copies.

### 6.5 Import and export

- **Ingredients:** `readIngredientFile` validates the file. Entries identical to the repository version are not stored locally. Entries whose unit differs from the current unit open the conversion dialog. **Cancel import** stops without changes. **Convert and import** applies the factors through `convertUsage`, then stores the entries.
- **Recipes:** `readRecipeFile` validates the file against the rules. The valid recipe is saved in `coxi-recipes`.
- **Inventory:** `parseInventory` validates the file. The inventory is stored as given, without unit checks.

### 6.6 Sharing

- The share link is the current page address with the query string of the plan.
- Pasting a link takes only its query string. The page then reloads with that query string, which replaces the plan. The stored inventory is kept.

### 6.7 Deleting local data

The settings button "Delete all local data" asks for confirmation, removes the four storage keys (`coxi-plan`, `coxi-inventory`, `coxi-recipes`, `coxi-ingredients`) and reloads the main page without query string.

## 7. PDF documents

All definitions come from `js/pdf/documents.js` and use A4 portrait. Fonts are Roboto from the vendored `vfs_fonts.js`, so umlauts and the euro sign are available.

- **Recipes PDF (main page):** one page per planned row. Amounts scaled by `portions / servings`. Shows the type, portions, portion weight, date and the working steps.
- **Recipe PDF (recipe page):** one page with the base amounts.
- **Sorting list:** three sections (Mains, Spreads, Others), each with name and summed amount.
- **Labels:** `LABEL_LAYOUT` sets 2 columns and 6 rows per page. Each label has the recipe name and the sorted, de-duplicated ingredient names separated by `LABEL_SEPARATOR`. Line height is `LABEL_LINE_HEIGHT`. The label size is derived from the page height, not hard-coded.
- **Shopping list:** groups by shop, columns Ingredient, Needed, In stock, To buy, Packages and an empty square for ticking off. Ends with the price estimate and a note about lower bounds if prices are missing.
- **Inventory PDF:** one section per category with the stored amounts.

File names: `recipes-<event>.pdf`, `sorting-list-<event>.pdf`, `labels-<event>.pdf`, `shopping-list-<event>.pdf`, `inventory-<name>.pdf`. The event name is slugified and omitted when empty.

## 8. Service worker and offline use

- `sw.js` is in the project root, so its scope covers the whole app. It is registered by `js/pwa.js` on every page.
- **Install:** stores every file in `SHELL_FILES`, then every recipe file listed in `recipes/index.json`. If one file is missing, the installation fails and the old worker stays active.
- **Fetch:** network first. Every successful response is stored. If the network fails, the stored response is used.
- **Query strings:** page requests (navigation) are stored and read without their query string. That is why a plan in the address works offline.
- **Cache name:** `CACHE_VERSION` (currently `coxi-v2`). Older caches are deleted on activation. The version is changed only when files move or caches must be reset.
- **Rule:** every new JavaScript, CSS or HTML file must be added to `SHELL_FILES`, otherwise it is missing offline.
- The web app manifest (`manifest.webmanifest`) defines the name, colors and icons. The iOS icon is `icons/apple-touch-icon.png`.

## 9. Data check and CI

### 9.1 Scripts

- `npm run validate` runs `scripts/validate-data.js`. It validates `ingredients/ingredients.json`, `inventory/inventory.example.json` and every file in `recipes/` against the schemas. Then it checks the shape of `recipes/index.json` and runs `validateDataset`: duplicate ids, file names that differ from recipe ids, unknown ingredient references, recipes missing in the index and index entries without files.
- `npm run build-index` runs `scripts/build-index.js`, which rewrites `recipes/index.json` from the recipe files.

### 9.2 GitHub Action (`.github/workflows/validate.yaml`)

- Runs on pull requests and on pushes to `main`.
- Steps: checkout (the pull request branch), Node 22, `npm ci`, `npm run build-index`, `npm test`, `npm run validate`.
- For pull requests from the same repository, a commit "Update recipe index" is pushed to the pull request branch if `recipes/index.json` changed. Pull requests from forks get no commit, so their index must be correct before they are opened.
- The workflow has `contents: write` permission for this push.
- Branch protection (required check before merge) is configured on GitHub, not in the repository.

## 11. Conventions

- Plain ES modules, JSDoc types, `// @ts-check` at the top of each file.
- All code, comments, data, user-facing texts and error messages are in English.
- Calculations are not rounded. Display rounding happens in `format.js`.
- Missing optional data does not throw. It produces `null` values and a visible "No price" or "Uncategorized" label.
- Business logic goes to `js/core/` and must not touch the DOM.
- Styles: `style.css` holds the general look only. Layout and page-specific rules go to `app.css`.

## 12. Known issues

- **Discarding a unit conversion:** if an ingredient's unit was changed with a conversion, "Discard local changes" restores the repository unit without converting the recipe amounts back. The recipe amounts then stay in the converted unit. The problem is not fixed yet.

Further limitations (no recipe name uniqueness, no update notification for the service worker) are listed in `docs/LLM_CONTEXT.md`.
